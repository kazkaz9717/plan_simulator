# 通信プラン料金シミュレーター（plan_simulator）

携帯ショップの店頭スタッフが、顧客への料金案内をスムーズに行うための**料金シミュレーションツール**です。
複数の料金プラン・割引・サブスク・オプション・手数料・機種を組み合わせて月額料金を即座に計算し、最大3パターンを並べて比較できます。

> 携帯ショップでの販売・接客経験から、「複雑な料金プランを正確かつ素早く案内したい」という現場の課題を解決するために制作しました。

## ✨ 主な機能

### シミュレーター（メイン機能）
- **動的な料金計算**: プラン・割引・サブスク・オプション・手数料・機種を選ぶと、月額料金と当日支払額をリアルタイムに自動計算
- **グループ単位の選択制御**: 料金プランや割引はグループごとに排他選択（いずれか1つ）、サブスク・オプション・手数料は複数選択に対応
- **時間経過に応じた段階表示**: 期間限定割引の終了や、機種・オプション・手数料の分割払いの完了を考慮し、「1〜12ヶ月目」「13〜24ヶ月目」「25ヶ月目以降」のように、料金が変わる節目ごとに月額を段階表示
- **分割払い計算**: 機種・オプションを一括／12・24・36・48回払いで切り替え、月額・当日払いに自動振り分けができ、手数料は当日・翌月のどちらかを選択可能
- **複数プラン比較**: 最大3パターンを横並びで比較。空から追加・既存をコピーして追加・個別削除が可能
- **詳細表示と印刷**: 選択内容の詳細を表示し、印刷用に整形して出力（顧客への提示用）

### 管理機能（管理者のみ）
- 料金プラン・割引・ブランド・サブスク・オプション・手数料・メーカー・機種・ユーザーの**CRUD**
- 各マスタの**グループ分け表示**、ブランド／メーカーによる**タブ絞り込み**
- 権限・登録日順でのユーザー一覧表示

### 認証・認可
- `has_secure_password` によるログイン認証
- 一般／管理者の権限管理（enum）と、管理画面へのアクセス制御
- ゲストログイン機能

## 💡 実装上の工夫

### 状態とUIの分離（シミュレーター設計）
シミュレーターでは、ユーザーの選択内容をJavaScriptの「状態オブジェクト」として一元管理し、画面表示と切り離す設計にしました。これにより、タブの切り替えや最大3件の比較を行っても各シミュレーションの選択が保持されます。

### 時間軸を考慮した料金計算
「特定の月における月額」を求める関数を用意し、割引の終了月・機種やオプション、手数料の分割完了月をすべて「料金が変わる節目」として収集することで、時間経過に応じた料金推移を正確に段階表示しています。

### 柔軟なグループ分類へのリファクタリング
当初は料金プランを固定カテゴリ（データ/音声/キッズ）で分類していましたが、運用で分類を自由に変更できるよう、`group_name` による可変グループ方式へリファクタリングしました。これにより全マスタで統一的なグループ分けを実現しています。

### Fat Model, Skinny Controller
並び替えや絞り込みのロジックを `scope` としてモデルに集約し、コントローラーを簡潔に保っています。

### パフォーマンス・セキュリティ
- 一覧取得時に `includes` を用いて関連データを先読みし、N+1問題を回避
- ストロングパラメーターによるマスアサインメント対策、権限に応じたアクセス制御を実装

## 🔧 苦労した点と解決策

### デプロイ後、ドメインにアクセスすると "no available server"
初回デプロイ後、割り当てられたドメインにアクセスすると原因不明のエラーに遭遇。まずアプリのコンテナ自体を疑い、実行ログを確認したところPumaは正常に起動しリクエストを待ち受けている状態でした。そこでコンテナより手前の層(DNS・リバースプロキシ)を順に切り分けたところ、DNSは正常、コンテナも稼働中にもかかわらず、Coolifyのリバースプロキシ(Traefik)自体が停止していることが判明。プロキシを再起動しても症状は変わらず、さらに調査を進めた結果、根本原因はドメインの登録が`http://`のままでHTTPS用の証明書(Let's Encrypt)が発行されていなかったことでした。ドメイン設定を`https://`に切り替えることで解決し、以降のトラブルシューティングでは、表面的なエラーメッセージだけでなく、プロキシの稼働状況や証明書の発行状況まで含めて手前から順に切り分ける習慣がつきました。

### ブランド削除時、「孤児になるレコード」だけを判定して連動削除する
`PlanBrand`と`Plan`・`Discount`は中間テーブル(`plan_brand_plans` / `discount_plan_brands`)を介した多対多の関係にあり、1つのプランや割引を複数のブランドで共有できる設計にしています。ここでブランドを削除する際、「そのブランドにしか紐づいていないプラン・割引」だけを一緒に削除し、他のブランドとも共有されているものは残す、という仕様が必要になりました。

素朴に実装すると、`dependent: :destroy`でブランド本体と一緒に中間テーブルのレコードを先に消してしまい、その後で「このプランは元々いくつのブランドに紐づいていたか」を判定しようとしても、既に紐付け自体が失われているため正しく判定できないという問題にぶつかりました。この順序を整理し、ブランド本体を削除する前に、紐づく各プラン・割引について`plan.plan_brands.count == 1`(＝このブランドが唯一の紐付け先)かどうかを判定して孤児になるものだけを先に削除し、そのあとでブランド自体を削除する、という処理順に組み立て直すことで解決しました。プラン・割引という2系統の多対多関係に対して同じ判定ロジックを並行して適用する必要がある点も、条件を揃えて実装する上でのポイントになりました。

### シミュレーションのコピー時に、元のデータまで一緒に書き換わってしまう問題
「コピーして追加」機能で、既存のシミュレーション状態を複製して新しいシミュレーションを作る際、単純にオブジェクトを代入しただけではプラン・オプションなどの内部配列が参照渡しのまま共有されてしまい、コピー後に片方を編集するともう片方まで意図せず変わってしまう不具合に遭遇しました。原因はJavaScriptのオブジェクト代入が参照渡しであることを見落としていた点にあり、`JSON.parse(JSON.stringify(state))`で状態オブジェクトを完全に複製(ディープコピー)する処理に変更することで、最大3件のシミュレーションを完全に独立させて編集できるようにしました。

### 割引や分割払いの終了タイミングがバラバラで、月額の変化を正確に表示できない問題
プラン・割引・機種やオプションの分割払いはそれぞれ適用期間や終了月が異なるため、単純に「現在の月額」を1つだけ表示すると、数ヶ月後に割引が切れたり分割払いが完了したりして実際の支払額が変わることを利用者に伝えられませんでした。そこで、割引の終了月・機種やオプションの分割終了月など「料金が変わるすべての節目(月)」を洗い出してソートし、区間ごとに月額を計算し直すことで、「1〜12ヶ月目」「13ヶ月目以降」のように支払額の変化を段階的に正確に提示できるよう設計しました。

## 🚀 ローカル環境での起動

```bash
# リポジトリをクローン
git clone https://github.com/kazkaz9717/plan_simulator.git
cd plan_simulator

# 依存パッケージをインストール
bundle install

# データベースを作成・初期化
rails db:create
rails db:migrate
rails db:seed

# サーバーを起動
rails server
```

ブラウザで `http://localhost:3000` にアクセスし、ゲストログインからお試しください。
